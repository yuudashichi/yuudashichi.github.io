Ragent

基础

基本概念

  • 大模型的参数：

    指神经网络中的权重（Weight）和偏置（Bias）的总数量。

    参数数量和能力不是线性关系，存在边际效应。

    参数不是越多越好，越多推理成本也越高。

  • Token：是模型内部的最小处理单元，模型通过分词器（Tokenizer）把文本切碎后的小片段。

  • 上下文窗口：指模型单次能处理的最大 Token 总数

  • Temperature：控制输出的随机性与发散度

    • 通过最终概率 = Softmax(原始得分 / T)来影响输出概率

      当T < 1时放大了每种可能的概率差距，头部少数词占据绝大多数概率

      T > 1则缩小概率差距，整个概率分布变得非平坦，低概率词也获得了被选中的概率

    • 不同场景下Temperature的推荐值

      场景 推荐 Temperature 原因
      RAG 问答 0~0.3 需要准确回答，不要发挥
      代码生成 0~0.2 代码需要精确，不能有随机性
      日常对话 0.5~0.7 需要自然流畅，但不能太离谱
      创意写作 0.7~1.0 需要多样性和创造力

  • MOE混合专家架构：

    Mixture of Experts，每次推理时只激活其中一部分专家（参数）来处理当前输入

  • 基座模型 / Chat模型：

    • 基座模型：完成预训练阶段后的原始大模型，只做预测，会根据文本一直往下续写
    • Chat 模型：在基座模型的基础上，先用高质量的「指令 - 回答」「多轮对话」数据做有监督微调（SFT），再通过 RLHF、DPO 等人类反馈算法，对齐人类的输出偏好与安全要求

  • 大模型生成回答的流程：

    1. 输入预处理：

      发送句子，首先会被分词器按照词表规则切分成一串 Token 序列；

      每个 Token 会被映射为词表中对应的数字 ID，再通过嵌入层（Embedding）转换成高维向量；

      同时会加入位置编码，向模型标注每个 Token 在句子中的先后顺序；

    2. 语义编码：

      自注意力机制会计算每个 Token 与其他所有 Token 的关联强度，比如 “天气” 和 “怎么样” 是强关联关系，从而解析出整句话的语义、语法、指代逻辑；

      经过多层网络的特征提取后，模型会得到对整段输入的完整语义表示；

    3. 自回归循环：

      基于当前的全部上下文（输入 + 已经生成的回答内容），模型计算出词表中所有 Token 的概率分布，也就是每个 Token 作为 “下一个词” 的可能性大小；

      从概率分布中选出一个Token，作为本轮的输出；

      把新生成的Token拼接到上下文的末尾，作为下一次的上下文；

    4. 终止条件：

      模型生成结束Token；

      达到了预设的最大输出Token长度；

      触发安全内容规则；

      生成的完整 Token 序列，会被分词器还原回自然语言文本。

OpenAI的API协议格式

请求格式

  • model：必填，指定使用的模型
  • messages：必填，对话历史数组，按时间顺序排列，每个消息对象包含：
    • role：消息角色，可选 system（系统提示，设定 AI 行为）、user（用户输入）、assistant（AI 历史回复）
    • content：消息内容，纯文本为字符串；多模态场景下为数组，可包含图片 URL
  • temperature：可选，默认 1，控制回复随机性，取值 0~2，值越低回复越确定
  • max_tokens：可选，限制单次回复的最大 token 数量
  • stream：可选，默认 false，是否开启流式输出（SSE 格式，用于打字机效果）

响应格式

外层通用字段

  • id：本次请求的唯一标识，用于问题排查和日志追溯
  • object：固定为 chat.completion，标识响应的类型
  • created：请求创建的 Unix 秒级时间戳
  • model：实际响应使用的模型完整版本号
  • system_fingerprint：模型后端指纹，相同指纹代表模型输出逻辑一致，用于可复现性验证
  • choices：回复结果数组，默认仅 1 条；通过 n 参数可请求多条备选回复
  • usage：Token 消耗统计，用于计费核算

choices 内部字段

  • index：结果序号，从 0 开始
  • message：完整的助手回复对象
    • role：固定为 assistant
    • content：回复的完整文本内容（工具调用场景下可能为 null）
  • finish_reason：回复终止原因，常见取值：
    • stop：正常结束，模型输出完毕
    • length：达到 max_tokens 上限被截断
    • content_filter：触发内容安全策略被拦截
    • tool_calls：模型发起了工具 / 函数调用
  • logprobs：Token 概率详情，默认关闭，开启 logprobs 参数后返回

usage 字段

  • prompt_tokens：输入侧（系统提示 + 历史对话 + 用户消息）消耗的 Token 数
  • completion_tokens：输出侧模型回复消耗的 Token 数
  • total_tokens：总消耗 Token 数

Prompt 的基本结构

要素 作用 对应环节
角色（Role） 定义模型是谁，边界是什么 处理
任务（Task） 定义模型要完成什么 处理
约束（Constraints） 定义禁止、优先级、风格、长度、来源限定 处理
输入（Inputs） 定义有哪些输入块、各自可信度、分隔符与字段规范 输入
输出（Outputs） 定义输出结构、引用规则、兜底与澄清问法 输出

在发布或更新 Prompt 之前，用这个清单检查一遍，确保没有遗漏关键要素：

检查项 说明 是否完成
✓ 角色定义 是否明确定义了模型的角色和边界 □
✓ 任务描述 是否清晰描述了模型要完成的任务 □
✓ 知识来源限定 是否明确只能依据参考资料回答 □
✓ 抗注入防护 是否定义了参考资料中的指令无效 □
✓ 指令优先级 是否定义了冲突处理的优先级（系统规则 > 用户问题 > 参考资料） □
✓ 信息不足处理 是否定义了信息不足时先澄清 □
✓ 输出格式规范 是否明确了引用位置、段落结构、长度上限 □
✓ 引用质量标准 是否要求没有引用就不输出该事实 □
✓ 兜底模板 是否提供了完全找不到信息时的兜底回复 □
✓ bad case 覆盖 是否针对已知的 bad case 添加了对应的修复条款 □

文本分块

关键参数：

  • chunkSize：每个块的长度上限。太大精度下降；太小句子的完整意思会被分开
  • overlap：相邻两个块之间共享的文本长度

分块策略

分块策略 描述 优点 缺点 适用场景
固定大小分块（FixedSize chunking） 将文本按固定大小切成块 实现简单 切断语义 文本结构不重要的场景，比如日志文件、纯数据文本
重叠分块（Overlapping Chunking） 相邻两个块之间留一段重叠区域 实现简单 仍然不看文本内容，只是用重叠来弥补 大多数通用场景的入门方案
递归分块（Recursive Chunking） 维护一个分隔符列表，按优先级从高到低排列；先尝试用最大的分隔符切，切完如果某个块还是太大，就换一个更小的分隔符继续切 兼顾了语义完整性和块大小控制 分隔符列表需要根据语言调整 绝大多数场景
语义分块（Semantic Chunking） 按句子拆开并向量化；计算句子间向量相似度；当相似度低于阈值就分块 每个块在语义上是高度内聚的 需要调用 Embedding 或者 Chat 模型，有额外的计算成本和延迟 对检索精度要求很高的场景
混合分块（Hybrid Chunking） 组合多种策略

向量化

将文本转换为高维向量，语义越接近的向量在空间上的距离会相近

Embedding模型

将输入的模型转换成向量

关键特征：

  • 输入长度有限制
  • 输出维度固定
  • 只有同一个模型输出的向量算相似度才有意义

相似度计算方法：

  • 余弦相似度：两个向量的点乘 / 两个向量模长的乘积
  • 欧氏距离
  • 点积

向量数据库

向量数据库 = 向量存储 + ANN 索引 + 高效检索

主流ANN算法

Approximate Nearest Neighbor，近似最近邻搜索

  • IVF（Inverted File Index，倒排文件索引）
    • 工作方式：
      1. 用聚类算法对所有向量做聚类，得到nlist个聚类中心（质心）
      2. 每个向量被分到最近的聚类中心的簇里
      3. 拿到查询向量后，计算和每个中心点的距离，找到最近的nprobe个簇
      4. 在这几个簇里做精确搜索，逐条和查询向量计算真实的向量距离，返回TopK个结果
  • HNSW（Hierarchical Navigable Small World Graph，分层可导航小世界图）：
    • 工作方式：
      1. 有多层，最底层包含说有节点，越往上节点能出现的概率呈指数降低，上层是下层的子集，节点和附近的M个邻居建立连接
      2. 查询时采用贪心搜索：从最高层的入口节点开始，不断跳向离查询向量更近的邻居，直到找不到更近的节点，之后以这个节点作为新入口找下一层，直到找到最底层。

检索

关键词检索

弥补向量检索强语义弱关键词的缺点

BM25算法

Best Matching 25，信息检索领域最主流的相关性打分算法，用来衡量一个查询词在某个文档中有多重要。它是搜索引擎（如 Elasticsearch）的默认排序算法，也是混合检索中关键词检索部分的核心。

通过对给定的查询语句，给每一篇候选文档计算相关性评分

评分规则：

  • 词频（TF）：词出现的次数越多分数越高，词频和分数关系呈对数关系，防止长文档天然优势
  • 逆文档频率（IDF）：越稀有的词越有区分度，词在所有文档中出现的次数越低，权重越高
  • 文档长度归一化：文档越长，会受到一定的长度惩罚，避免长文档仅凭篇幅优势得分虚高

混合检索

同时执行向量检索和关键词检索，把两路结果融合成一个最终排序；

两种检索的分数不能直接做比较，需要做融合

RRF（倒数排名融合）

不看分数，只看排名的位次

公式：

  • rank_i(d) 是 chunk d 在第 i 路检索中的排名（从 1 开始）
  • k 是一个平滑常数，通常取 60
  • Σ 表示对所有检索路求和

重排序

检索阶段目标是快速召回尽可能多的相关结果，但排序不一定精准，需要对结果进行重排序，用更强的模型对候选集重新打分，把最相关的结果排到最前面

基本流程：

  1. 初检阶段（向量检索 / 混合检索）快速召回候选集，比如 Top-20 或 Top-50
  2. 重排序模型逐个评估这个 chunk 和用户问题到底有多相关，给每个候选打分
  3. 按重排序分数重新排序，取 Top-K作为最终结果

MCP

Model Context Protocol，实现了MCP协议的工具就能被支持MCP协议的客户端调用。解决工具的定义、发现、注册、权限和管理等问题，对工具的标准化管理。

MCP核心能力：

  • 工具调用（Tools）
  • 资源访问（Resources）：Host主动从MCP Server读取的数据，然后发给模型，如预先读取用户的个人资料
  • 提示词模板（Prompt）

MCP调用协议

MCP调用协议选择的是JSON-RPC 2.0，为了在协议层统一“请求—响应—通知”的表达方式。

JSON-RPC 2.0 是一种轻量级远程过程调用（Remote Procedure Call，RPC）协议。它规定了请求和响应的数据格式，使用 JSON 来表示消息，但不限定底层传输协议。

工具设计原则

工具定义设计原则：

  • 单一职责原则：一个工具只做一件事，不要把多个功能塞进一个工具
  • 参数最小化原则：只暴露必要的参数，不要把所有可能的参数都加上
  • 幂等性原则：操作类工具要设计成幂等
  • 返回值结构化原则：返回结构化的 JSON，包含足够但不冗余的信息，错误响应要包含错误码和错误信息

会话记忆

记忆保存策略

  • 完整历史：每次请求都带上所有历史消息

  • 滑动窗口：保留最近N轮对话

  • Token截断：设置Token上限，超出上限的消息直接丢弃

    截断时要保证成对丢弃——一轮对话的 user 和 assistant 消息要么都保留，要么都丢弃

  • 摘要压缩：用大模型把早期对话压缩成一段简短的摘要

    触发策略 做法 优缺点
    按轮数触发 每隔 N 轮（如每 5 轮）压缩一次 简单直接，但不够灵活，短消息也触发浪费
    按 Token 阈值触发 对话历史超过 M Token（如 3,000 Token）时压缩 更精确，推荐使用
    按话题切换触发 检测到用户换了话题时压缩上一段对话 效果最好，但话题切换检测本身有难度

  • 混合策略：早期对话压缩成摘要+最近N轮保留完整对话

记忆存储方法

Redis做主存储+MySQL做归档 。对话进行时，消息存 Redis（快速读写）；对话结束后，异步写入 MySQL（持久化、审计）

维度 内存 Redis 数据库（MySQL）
读写性能 极快（纳秒） 快（毫秒） 较慢（毫秒~十毫秒）
持久化 不支持 可选（AOF/RDB） 天然支持

适用场景 开发调试 生产环境 审计 / 分析场景

系统化评估

用量化的指标来评判生成回答的好坏

评估指标

检索阶段：

  • 命中率（Hit Rate）：对多个测试问题，每个问题召回的Chunks里有没有包含正确答案。不关心正确的答案排在第几

  • 平均倒数排名（Mean Reciprocal Rank）：正确答案越靠前得分越高。排在第 1 位，得 1 分；排在第 2 位，得 1/2 = 0.5 分……，排在第 K 位，得 1/K 分。如果 Top-K 里没有正确答案，得 0 分。多个问题取平均。

  • 召回率（Recall）：答案分散在多个Chunk里。所有包含答案的Chunk，找到了几个

  • 精确率（Precision）：召回的Chunk里有几个是相关的

    设置的Top-K大，召回率就高、精确率就低；反之则召回率低、精确率高

生成阶段：

  • 忠实度（Faithfulness）：模型生成的答案是否忠实于检索到的 chunk 内容，有没有编出 chunk 里没有的信息
  • 答案相关性（Answer Relevancy）：模型生成的答案是否回答了用户的问题（不管对不对）

端到端的评估：

  • 答案正确率：最终答案是否正确回答了用户的问题
  • 兜底率：当检索不到相关 chunk 或者模型判断无法回答时，返回兜底回复
  • 用户满意度

文档上传与处理流程

文档上传和处理是分开处理的

  1. 用户上传文档，文档被存进Postgre中，文档状态为pending，此时不触发分块处理
  2. 前端点击执行分块，文档状态通过CAS操作改为running，防止重复触发。
  3. 发送消息到消息队列，异步执行分块、向量化和存储，完成后状态改为success

文档处理

上传

请求URL：/knowledge-base/{kb-id}/docs/upload

主要流程：

  1. 校验知识库是否存在

  2. 解析文件来源：如果是本地上传，把文件保存到对象存储；如果是 URL 抓取，先从 URL 下载文件再保存

    • 本地文件：通过fileStorageService.upload 使用预签名 URL 流式上传到 S3 兼容存储（RustFS），不会把整个文件读到内存中。
    • URL：先请求远程文件的响应头得到文件类型和大小，预判断大小是否超过预设；先下载到临时文件校验真实大小是否超过预设，然后再上传到对象存储并删除临时文件

  3. 插入记录：在 t_knowledge_document 表插入一条记录，设置status=pending，记录文件路径、类型、大小、分块配置等

    整个文件上传流程没有加事务，是因为网络IO的时间可能很长，加事务会一直占着数据库连接。

    如果出现文件上传了但数据库失败的情况，通过定时扫描和删除对象存储里没有引用的文件来解决。

  4. 返回响应：返回文档 ID 给前端

触发分块

请求URL：/knowledge-base/docs/{doc-id}/chunk"

主要流程：

  1. 发送MQ半事务消息：把本地数据库操作和发送消息绑定成原子操作

    如果发送半事务消息后，没有告知MQ事务成功还是失败，会触发MQ的事务回查，触发RocketMQLocalTransactionListener的checkLocalTransaction()，返回对应文档的状态

  2. 执行本地事务：用原子操作把 status 改成 running，如果已经是 running，说明有人在处理，直接拒绝，避免重复触发；如果文档配置了定时刷新，注册或更新定时任务

  3. 发送MQ确认事务消息：告知消费者可以开始分块，触发异步处理

  4. 立即返回：不等处理完成，直接返回成功

分块

  1. MQ消费者监听器KnowledgeDocumentChunkConsumer收到分块消息

  2. 解析文件：从数据库中获取文档，使用Apache Tika从原始文件中提取纯文本

  3. 分块：根据文档配置的 chunkStrategy 和 chunkConfig 配置执行分块（Chunk或Pipeline），生成chunk列表

  4. 向量化：调用Embedding API，批量处理文本

  5. 存储：开启事务，删除旧的chunks和vectors，批量插入chunks和vectors，完成后将文档的status改成success，提交事务

    只在保存的时候开启事务，不在事务内做分块等耗时操作

执行定时任务

线上文档会不定时更新，需要定时抓取

  1. KnowledgeDocumentScheduleJob：开启定时任务
    • 每10s扫描一次数据库，找已经到执行时间的任务，尝试获取锁，然后提交到线程池中执行
    • 每30min扫描一次数据库，把卡在 RUNNING 状态超过阈值（默认 30 分钟）的文档重置为 FAILED，这是进程崩溃后的兜底恢复机制。
  2. ScheduleLockManager：负责分布式锁的获取、续期、释放，以及自动心跳续锁机制
    • 获取锁：生成唯一lcokToken、计算过期时间（当前时间 + 15min）、尝试更新表把锁的持有人改为自己、成功返回凭证/失败返回null
    • 自动心跳续锁：获取锁后，创建一个定时任务到线程池，固定周期（5min）延长锁的时间，如果续锁失败（锁被其他实例抢走），则立即终止执行和停止心跳检测
    • 释放锁：检测是不是自己的锁，把持有人设为NULL
  3. ScheduleStateManager：负责更新 schedule 表和 exec 表的状态
  4. DocumentStatusHelper：负责文档状态的 CAS 更新和恢复
  5. RemoteFileFetcher：远程文件变更检测，只在远程文件变更时才更新本地文件
    • 第一级检测：发送HEAD请求，只获取资源的响应头，查看ETag（资源唯一标识）和Last-Modified（最后修改时间）
    • 第二级兜底：服务器不支持HEAD请求或元数据变动时，下载资源并计算SHA-256，和本地文件比对
  6. ScheduleRefreshProcessor：执行定时任务，负责完整的刷新流程编排，是定时同步的总控台
    • 锁失效检测：检测心跳检测是否停了、尝试续锁一次。不止在心跳检测时检测锁，在高成本操作（抢占文档运行权、分块）前也会检测，防止锁失效了还在执行
    • 准备阶段：
      • 启动定时心跳检测
      • 校验任务合法性：检查文档是否存在；是否已禁用；cron表达式是否有效等
      • 创建执行记录：记录执行的是哪个知识库的哪个文档；开始时间；用于后续问题排查
    • 执行阶段：
      • 检测远程文件是否变更
      • 检测锁是否失效并续期（上传文档）
        • 将文档状态改为RUNNING（抢占文档运行权）
        • 上传文档到对象存储
        • 更新数据库中文档的存储url、名称等内容
      • 检测锁是否失效并续期（文档分块）
        • 文档分块
        • 回查文档，判断是否分块成功
    • 收尾阶段：
      • 关闭心跳检测
      • 删除旧文档
      • 释放锁

分布式锁选型：

选择用数据库来实现分布式锁，理由：

  • 定时任务调度状态表t_knowledge_document_schedule已经存在，只需加上两个字段锁的拥有者和过期时间就可以实现定时任务粒度的锁
  • 定时任务的扫描频率不高
  • 出问题直接查数据库的调度状态表就行，排查错误方便，不需要再去查询Redis

上传限流

限制正在上传的文件数量，防止磁盘IO飙升；

通过Redisson的分布式信号量和OncePerRequestFilter过滤器实现限流

主要过程：

  1. 在Filter 层限流，可以让multipart 不会被解析，只有在真正读取时才会产生临时文件，减少磁盘IO
  2. 在过滤器中判断请求类型，如果是上传文件则尝试获取信号量
    • 信号量为0则直接终止请求
    • 信号量不为0则放行请求
  3. 在finally中释放信号量

每家供应商的调用方式仅存在微小差异，因此使用**AbstractOpenAIStyleChatClient抽象类，应用模板方法，将相同的请求构建、HTTP 调用、响应解析、错误处理等放在抽象基类，不同的认证方式、特殊字段等通过钩子方法留给子类覆写**

抽象类的子类可覆写的方法：

  • requiresApiKey()：是否需要api认证（本地Ollama不需要）
  • customizeRequestBody()：添加供应商特有字段
  • isReasoningEnabledForStream()：流式调用时是否解析 reasoning_content 字段

调用方式：

  • 同步调用：基类通过**doChat()**将调用模型的过程串了起来，里面抽象方法的具体实现由子类完成，模型生成完一次性返回所有内容
  • 流式调用：**doStreamChat()**

流式对话流水线八阶段

**StreamChatPipeline**，在将用户提问发给LLM之前的操作

  1. 防护
    1. 幂等拦截
    2. 限流拦截
  2. 加载会话记忆：将完整的会话记录添加到ctx.history
  3. 查询改写与子问题拆分：把用户的原始问题改写成更适合检索的形式，同时把复合问题拆成多个子问题
  4. 意图识别：对每个子问题应该去判断哪个知识库、调哪个工具、还是系统直接回答
  5. 歧义引导：检测多个意图之间是否存在歧义，如果有就反问用户，让用户自己选
  6. 系统直答：所有意图都是SYSTEM，则跳过RAG检索直接调LLM
  7. 多通道检索：若为KB意图，对每个命中的知识库并行发起向量检索，检索结果经过去重、精排（Reranker）等后处理，最终筛选出最相关的几条文档片段；若为MCP意图，调用外部系统的 API 获取实时数据
  8. 空结果兜底：如果知识库和工具都没有返回任何结果，直接告诉用户没找到
  9. 组装Prompt、流式生成：把对话历史、检索结果、工具数据、系统 Prompt 拼成完整的消息列表，调大模型流式生成答案

阶段间通过StreamChatContext传递参数

加载会话记忆

  1. 并行加载早期会话摘要和历史记录

    历史记录加载最近的8轮对话（共16条消息）

  2. 保存当前的用户问题并判断是否触发压缩（异步）
