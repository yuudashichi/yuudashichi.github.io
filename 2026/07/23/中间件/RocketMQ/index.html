RocketMQ

概念

Apache RocketMQ 是一个分布式消息中间件，最初由阿里巴巴开发，后捐赠给 Apache 基金会，适用于高并发、高吞吐、高可靠的异步通信场景。

用于在不同系统之间可靠地传递消息，实现系统解耦通信、异步处理和流量削峰。

官网：https://rocketmq.apache.org/

术语

  • Message（消息）：传输的基本单元，包含了具体的业务数据以及一些元数据
  • Topic（主题）：Topic 是一类消息的逻辑分类名，是 Apache RocketMQ 中消息传输和存储的顶层容器。一个 Topic 可以被多个生产者写入，同时也能被多个消费者订阅。
  • Queue（队列）：每个 Topic 被划分为多个 Queue，这些队列用于存储消息。生产者发送到 Topic 的消息会被分配到其下的各个 Queue 中；消费者则是从这些 Queue 中拉取消息进行消费。
  • Subscription（订阅）：消费者对某个 Topic 消息的兴趣表达。订阅关系由消费者分组动态注册到服务端系统，并在消息传输中按照订阅关系定义的过滤规则进行消息匹配和消费进度的维护。
  • Producer（生产者）：生产者是消息产生的源头，将消息发送到服务端指定 Topic。
  • Consumer（消费者）：消费者负责从服务端中拉取消息并进行处理。
  • ProducerGroup（生产者组）：是一组生产者的逻辑分组，共享同样的 Topic 发送配置，实现发送端的负载均衡和容错。如果组内某个生产者失败，其他生产者可以继续工作，保证消息发送的连续性。
  • ConsumerGroup（消费者组）：用于统一管理底层运行的多个消费者。同一个消费组的多个消费者必须保持消费逻辑和配置一致，共同分担该消费组订阅的消息，实现消费能力的水平扩展。

常用部署组件

  • Broker：RocketMQ 的核心服务节点，负责接收来自 Producer的消息、存储消息以及将消息转发给 Consumer
  • NameServer：是 RocketMQ 的路由服务集群，它不保存任何消息数据，而是维护着所有 Broker 的路由信息（包括 Broker 存活情况、各 topic 的路由信息等），在发送或订阅消息前，都需要先从 NameServer 获取 Broker 的路由信息，之后才能正确地与 Broker 通信
  • Proxy：作为一个轻量级的代理服务器，位于客户端与 Broker 之间。主要职责包括负载均衡、协议转换、安全控制、网络优化等
  • Controller：RocketMQ 5.0 新增的组件，负责管理和协调系统的整体状态。如 Broker 宕机时，它将进行调度，对 Broker 集群进行选举管理
  • Dashboard：RocketMQ 提供的一款可视化管理界面

典型应用场景

  • 削峰填谷与流量控制：RocketMQ 可以作为缓冲区，暂时存储大量涌入的请求，从而避免系统直接承受峰值压力
  • 异步解耦：解耦系统组件，允许服务间的异步通信
  • 顺序消息处理
  • 分布式事务支持
  • 延时消息与定时任务

下面创建生产者和消费者使用的工具类

普通消息

一般应用于微服务解耦、事件驱动、数据集成等场景，支持生产者和消费者的异步解耦通信

普通消息生命周期：

  • 初始化：生产者构建消息，待发送到MQ的状态
  • 待消费：消息被发送到MQ，对消费者可见，等待消费者消费的状态
  • 消费中：消息被消费者获取，并按照消费者本地的业务逻辑进行处理的过程。 此时服务端会等待消费者完成消费并提交消费结果，如果一定时间后没有收到消费者的响应，MQ会对消息进行重试处理
  • 消费提交：消费者完成消费处理，并向MQ提交消费结果，服务端标记当前消息已经被处理
  • 消息删除：Apache RocketMQ按照消息保存机制滚动清理最早的消息数据，将消息从物理文件中删除

事务消息

支持在分布式场景下保障消息生产和本地事务的最终一致性；

用于将发送消息也纳入到事务中；

保障的是最终一致性，中间上下游会出现状态不一致的情况

事务消息生命周期：

  1. 初始化
  2. 提交一阶段：半事务消息被发送到MQ，和普通消息不同，并不会直接被MQ端持久化，而是会被单独存储到事务存储系统中，等待第二阶段本地事务返回执行结果后再提交
  3. 提交二阶段：
    • 消息回滚：第二阶段如果事务执行结果明确为回滚，MQ端会将半事务消息回滚，该事务消息流程终止。
    • 提交待消费：第二阶段如果事务执行结果明确为提交，MQ端会将半事务消息重新存储到普通存储系统中，此时消息对下游消费者可见，等待被消费者获取并消费
  4. 消费中：消费者消费消息
  5. 消费提交：消费者提交消费结果
  6. 消息删除

使用示例

  1. 创建/更新一个Topic

    • -a +message.type=TRANSACTION：添加 Topic 属性，设置消息类型为事务消息

  2. 构建事务消息

消费者类型

SimpleConsumer

消息的获取、消费状态提交以及消费重试都是通过消费者业务逻辑主动发起调用完成

  • SimpleConsumer相对于PushConsumer方式更加灵活，适用于消息处理时长不可控、需要异步化、批量消费等高级定制场景

PushConsumer

在消费者初始化时注册一个消费监听器，并在消费监听器内部实现消息处理逻辑。由 Apache RocketMQ 的SDK在后台完成消息获取、触发监听器调用以及进行消息重试处理。

  • PushConsumer严格限制了消息同步处理及每条消息的处理超时时间，适用于消息处理时间可预估、无异步化、高级定制场景

PullConsumer

🌟生产环境中相同的 ConsumerGroup 下严禁混用 PullConsumer 和其他两种消费者，否则会导致消息消费异常。

机制

发送消息重试机制

在发送消息时，如果遇到网络故障、服务异常、请求超时、MQ端重启/下线、MQ端处理慢，或者服务端返回失败错误码，都会触发发送重试

生产者在初始化时会设置最大重试次数；触发后客户端会一直重试，直到发送成功或达到上限；

除“MQ端返回系统流控错误”之外，其他失败场景基本是立即重试；如果是因为流控错误触发重试，则会按指数退避延迟重试

流控机制

当系统容量或水位过高时，RocketMQ 服务端会通过快速失败来保护底层资源，避免压力继续放大

触发流控的情况：

  1. 存储压力大，比如消费位点回溯等场景会让队列存储压力瞬间升高
  2. 服务端请求任务排队溢出，也就是消费者消费能力不足、消息堆积过多时触发流控，用来降低下游压力

消费消息重试机制

业务处理失败、处理超时的时进行重试

PushConsumer的重试机制

当消费者返回处理失败或处理超时时，消息被设置为待重试状态，未到达最大重试次数就会在重试间隔后再次可被消费。否则会被投递至死信队列

SimpleConsumer的重试机制

当消费者返回处理失败时触发；

和PushConsumer消费重试策略的不同点是，SimpleConsumer消费者的重试间隔是预分配的，每次获取消息消费者会在调用API时设置一个不可见时间参数 InvisibleDuration，即消息的最大处理时长。若消息消费失败触发重试，不需要设置下一次重试的时间间隔，直接复用不可见时间参数的取值
