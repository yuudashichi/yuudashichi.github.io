Redis八股

Redis

数据结构

5种基本数据结构：String（字符串）、List（列表）、Set（集合）、Hash（散列）、Zset（有序集合）

3种特殊数据结构：Bitmap（位图）、HyperLogLog（基数统计）、Geospatial（地理位置）

String

应用场景：1. 常规数据（比如 Session、Token、序列化后的对象、图片的路径）的缓存；2.分布式锁；3.计数等

实现方式：使用自己实现的SDS（Simple Dynamic String，简单动态字符串）

SDS基本数据结构：

相比于C语言的字符串，SDS可以避免缓冲区溢出、减少内存分配次数等优点

List

链表数据结构

实现方式：

  • 当数据量较小时，使用ListPack：Listpack 是一块连续内存，多个元素紧凑排列
  • 当数据量较大时，使用Quicklist：Quicklist本质是一个双向链表，但每个节点存的不是单个元素，而是一个ListPack

ZipList基本数据结构：

ZipList存在连锁更新问题：一个元素的大小变大了，下一个元素的prevlen占用的字节数可能变多，导致后续一连串的元素都要更新。因此Redis7.0后ListPack替代了ZipList

  • prevlen：记录前一个元素占用的总字节数，用于从后向前遍历
  • encoding：记录元素类型和长度
  • entry-data：字符串或整数数据

ListPack数据结构：

backlen描述的是元素自身，不会连锁更新

  • encoding：元素类型及长度信息
  • element-data：字符串或整数数据
  • backlen：记录当前元素前半部分的长度，用于反向遍历

Set

无序集合。应用场景：1.判断是否点赞、统计点赞人数；2.交集运算找共同关注；3.随机获取

实现方式：

  • 当所有元素都是整数且数量不超过默认阈值 512 时使用IntSet：连续内存，元素有序排列
  • 小型非纯整数时用ListPack
  • 当元素数量或大小超过阈值时，转换为Hashtable

IntSet基本数据结构：

  • encoding：每个整数占 16、32 或 64 位
  • length：元素数量
  • contents：按数值升序排列的连续整数数组

ZSet

有序集合

实现方式：

  • 元素数量 ≤ 128 且member 长度 ≤ 64 字节时使用ListPack
  • 超过阈值后使用SkipList

SkipList基本数据结构：

有多级索引的有序链表，每层保存的是元素的指针，实际Redis中双向链表

  • 查询：从最顶层索引开始找，直到找到要的元素
  • 插入：先找到每一层的前序节点；然后随机一个最高层数（新的节点升层的概率为25%，最高允许32层），假设随机到了1层，则在0层和1层的前序节点后插入该节点
  • 修改：修改score时，若影响当前位置，则先删除再重新插入
  • 删除：找到每层的前序节点，然后将后序指针跳过待删节点

为什么使用跳表：

  • 和平衡树相比：平衡树也可以通过中序排序范围查询，但维护平衡树的平衡操作比较花时间
  • 和红黑树相比：插入删除操作比平衡二叉树更快，但跳表的实现更简单，且范围查找更快
  • 和B+树相比：B+树的核心思想是通过可能少的 IO 定位到尽可能多的索引来获得查询数据，但Redis是内存数据库，不会存那么多数据，因此不需要B+树来维护索引

Bitmap

基于 String 类型实现的位操作结构。连续的二进制位数组，每一位（bit）只能存储 0 或 1。

应用场景：需要保存状态信息（0/1 即可表示）的场景（用户签到情况、活跃用户情况、用户行为统计等）

HyperLogLog

用于在海量数据中，用极小的内存，估算集合中不重复元素数量的数据结构，也叫基数统计；

最大的优势是内存占用固定且很小

应用场景：网站 UV 统计、每日活跃用户数、搜索关键词去重数量、商品独立访问人数等，不适合精确计数

Geospatial

主要用于存储地理位置信息，基于 Sorted Set 实现；

可以轻松实现两个位置距离的计算、获取指定位置附近的元素等功能

应用场景：附近的人

使用场景

  • 缓存（穿透、击穿、雪崩、双写一致、持久化、数据过期、淘汰策略）、
  • 分布式锁（setnx、redisson）
  • 计数器（浏览量、点赞数）
  • 排行榜等

Redis为什么快：

  • Redis是基于内存的
  • 执行命令和核心数据结构操作采用单线程，避免了多线程模型中的上下文切换和锁竞争问题
  • 使用I/O多路复用模型，非阻塞IO（实现高效的网络请求）

✨生产问题

缓存穿透

查询一个既不在缓存也不在数据库的数据，导致每次请求都查询数据库

解决方式：

  1. 缓存无效key：缓存空数据，可能会缓存很多无效key占用内存

  2. 布隆过滤器：把所有可能存在的请求的值都存放在布隆过滤器中，拦截不存在其中的数据（内存占用小，存在误判的风险）

  3. 接口限流、IP黑名单

布隆过滤器

Bloom Filter，BF。主要是为了解决海量数据的存在性问题；

优点是占用内存少、效率高；

缺点是结果是概率性的，元素越多，误报的可能性就越大；已加入的元素不好删除

实现原理：

  • 使用一个较大的 bit 数组来保存所有的数据，数组中的每个元素都只占用 1 bit，并且每个元素只能是 0 或者 1
  • 通过多个哈希函数计算要加入元素的多个hash值，然后把对应位置置为1（减少hash碰撞概率）
  • 判断时要对应位置全部为1，才判断元素存在
  • 可能会因为hash碰撞造成误判

缓存击穿

请求的 key 对应的是热点数据，该数据存在于数据库中，但不存在于缓存中。导致大量瞬时请求打到数据库上

解决方式：

  1. 设置热点数据永不过期
  2. 提前预热热点数据，将数据存入缓存并设置合理的过期时间
  3. 加锁：第一个没查到缓存的线程获取互斥锁去重建缓存，其他线程等待
  4. 逻辑过期：添加逻辑过期字段，第一个发现过期的线程获取互斥锁，新开一个线程去重建缓存，其他线程返回旧数据

缓存雪崩

同一时段大量key同时过期或Redis服务宕机，导致大量请求打到数据库

解决方式：

  1. 搭建高可用Redis集群
  2. 设置多级缓存
  3. 设置随机的过期时间

性能优化

  • 使用批量操作减少网络传输，不仅减少了RTT（Round Trip Time，往返时间），还减少了Socket IO时系统调用导致的用户态/内核态切换开销

    批量操作可以使用原生批处理命令（原子操作）、Pipeline（非原子操作、非事务）、Lua脚本（非集群下原子操作）；

    注意：每次批量操作执行的命令数量不宜过多，因为Redis需要暂存请求/响应数据，会占用大量内存

  • 操作、读取bigkey很耗时，执行命令会阻塞线程、造成网络I/O堵塞

    发现bigkey：

    • 使用自带命令redis-cli -p 6379 --bigkeys
    • 使用开源的RDB分析工具

    处理bigkey：

    • 分割 bigkey：将一个 bigkey 分割为多个小 key
    • 手动清理：Redis 4.0+ 可以使用 UNLINK 命令来异步删除一个或多个指定的 key。Redis 4.0 以下可以考虑使用 SCAN 命令结合 DEL 命令来分批次删除
    • 采用合适的数据结构：例如，文件二进制数据不使用 String 保存、使用 HyperLogLog 统计页面 UV、Bitmap 保存状态信息
    • 开启 lazy-free（惰性删除/延迟释放）：让 Redis 采用异步方式延迟释放 key 使用的内存，将该操作交给单独的子线程处理，避免阻塞主线程

  • hotkey会占用大量的 CPU 和带宽，可能会影响 Redis 实例对其他请求的正常处理

    处理hotkey：

    • 读写分离：主节点处理写请求，从节点处理读请求
    • 使用 Redis Cluster：将热点数据分散存储在多个 Redis 节点上
    • 二级缓存：hotkey 采用二级缓存的方式进行处理，将 hotkey 存放一份到 JVM 本地内存中

双写一致性

指的是数据库和Redis的数据保持一致；

强一致会增大性能开销，因此需根据业务场景选择合适的策略

  • 读操作：缓存命中，直接返回；未命中查询数据库，设置超时时间写入缓存

  • 写操作：

    • 延迟双删：弱一致，先更新数据库再删除缓存，延迟一段时间后再删一次
    • 使用消息队列，将删除缓存重试的消息投递到消息队列，然后由专门的消费者来重试。队列的性质保证了成功消费之前不会丢失

不延迟双删可能出现的问题：

  • 先删缓存再更新数据库：删除缓存后又有线程重建了缓存，造成数据不一致
  • 先更新数据库再删缓存：此时key过期，另一个线程查到旧数据，待删除缓存后又重建缓存，造成数据不一致

持久化

用途：重启机器、故障恢复之后恢复数据；主从节点数据同步

RDB

Redis Database，在指定的时间间隔对数据集进行即时快照

Copy-On-Write机制：fork()时，子进程和父进程共享内存页；当内存页被修改时，会复制出该页的一个新页，在新页上修改，子进程继续使用旧页

优点：

  • RDB 是一个非常紧凑的单文件、即时快照形式的 Redis 数据表示，非常适合备份
  • 持久化数据时通过fork()创建一个子进程来执行，不影响父进程处理客户端请求
  • RDB相比于AOF能更快恢复大数据集

缺点：

  • 宕机时会丢失两个保存点之间的数据
  • fork()本身是阻塞的，数据量越大延迟越大
  • 大数据集 + 高写负载时，会导致大量页面复制，影响性能
  • Linux的THP（透明大页）会增大COW的内存开销

AOF

Append Only File，会记录服务器接收到的所有写操作，这些操作可以在服务器启动时重新播放，从而重建原始数据集；

AOF默认没有开启

基本流程：

  1. 命令追加：写操作执行完后，将命令追加到AOF缓冲区

  2. 文件写入：使用系统调用wirte()，将AOF缓冲区的数据写入内核缓冲区

    通常在处理一批客户端命令后主线程调用

  3. 文件同步：根据appendfsync配置的策略，在不同时机使用系统调用fsync()将数据写入磁盘

    always：每次写命令，主线程执行；everysec：每秒，后台子线程执行；no：不主动执行，交给系统决定

  4. 文件重写：定期重写来压缩AOF文件大小

AOF重写

在子进程中进行，根据当前的数据状态，生成恢复当前状态所需的最短命令序列

Redis7.0之前，父进程将重写期间的命令放入内存重写缓冲区，重写完成后追加到新AOF；

Reids7.0之后，父进程在重写期间同时新建一个增量 AOF文件（为了减少内存占用），记录重写期间的新写命令，重写完成后合并两个AOF

优点：

  • 安全性更高，支持秒级持久化
  • 可读性更强，RDB文件是二进制格式保存，AOF则以一种易于理解和解析的格式包含所有操作的日志

混合持久化

AOF 使用 RDB 格式保存基础数据，再使用 AOF 命令保存后续增量数据

混合持久化是在 AOF 重写时，用 RDB 保存全量基础数据，用 AOF 保存之后的增量操作，兼顾 RDB 的恢复速度和 AOF的数据安全性。

过期策略

  • 惰性删除：只在查询/使用key的时候才进行过期检查
  • 定期删除：周期性地随机从设置了过期时间的 key 中抽查一批，然后逐个检查这些 key 是否过期
  • Redis使用两种策略结合的策略

大量key的过期时间设置在同一时间可能会导致缓存雪崩

淘汰策略

在运行内存达到了配置的最大内存阈值时触发

  1. volatile-lru（least recently used）：从已设置过期时间的数据集（server.db[i].expires）中挑选最近最少使用的数据淘汰。
  2. volatile-ttl：从已设置过期时间的数据集（server.db[i].expires）中挑选将要过期的数据淘汰。
  3. volatile-random：从已设置过期时间的数据集（server.db[i].expires）中任意选择数据淘汰。
  4. allkeys-lru（least recently used）：从数据集（server.db[i].dict）中移除最近最少使用的数据淘汰。
  5. allkeys-random：从数据集（server.db[i].dict）中任意选择数据淘汰。
  6. no-eviction（默认内存淘汰策略）：禁止驱逐数据，当内存不足以容纳新写入数据时，新写入操作会报错。
  7. volatile-lfu（least frequently used）：从已设置过期时间的数据集（server.db[i].expires）中挑选最不经常使用的数据淘汰。
  8. allkeys-lfu（least frequently used）：从数据集（server.db[i].dict）中移除最不经常使用的数据淘汰。

分布式锁

使用Redis简单实现

SETNX：SET if Not eXists，如果 key 不存在的话，才会设置 key 的值

加锁：SETNX lockKey uniqueValue

释放锁：DEL lockKey，防止误删可以使用Lua脚本

加过期自动释放锁：SET lockKey uniqueValue EX 3 NX

使用Redisson实现

性质：

  • 原子性：加锁、设置过期时间都是通过Lua脚本实现的

  • 看门狗机制（Watch Dog）：如果操作共享资源的线程还未执行完成的话，Watch Dog会不断地延长锁的过期时间，进而保证锁不会因为超时而被释放

  • 重试机制：在一定次数内通过while循环尝试加锁，增加分布式锁的性能

  • 可重入：根据线程id判断是否是同一线程

  • 主从一致性：Redis主从复制默认异步。如果一个线程在主节点加锁后，主节点还没有和从节点同步数据就宕机了，此时另一个线程也来加锁，就会导致同一把锁被两个线程持有；

    Redisson通过RedLock（红锁）解决：让客户端向多个相互独立的 Redis master 依次请求申请加锁，至少获得N/2 + 1个节点成功才算成功；失败要释放所有锁。RedLock实现复杂、性能较差

使用：

集群

主从复制：搭建主从节点，实现读写分离，提高并发能力

主从同步

  • 通过replid判断主从节点数据的版本号，如果从节点没有replid表示第一次同步数据，主节点需要发送RDB文件（全量同步）
  • 如果不是第一次同步数据，则通过offset偏移量判断需要从repl_backlog中发送多少数据来更新从节点数据（增量同步）

哨兵模式：监控、故障恢复、通知

监控：心跳检测，监控主从节点是否能正常工作

故障恢复：主节点挂了选择offset大的从节点提升为主节点

通知：当集群发生故障转移时，通知Redis客户端

脑裂问题：主节点没有挂，而是由于网络延迟导致哨兵节点检测不到，从而又选了个主节点，原先的主节点强制变为从节点，而主节点里这段时间的写数据就丢失了。解决方式：设置主节点要有一定数量的从节点时才能接收写数据、设置主从同步延迟时间的上限

分片集群

解决海量数据存储和高并发写的问题

特点：

  • 集群中有多个master、每个master保存不同的数据
  • 每个master都可以有多个slave节点
  • master之间通过ping检测彼此健康状态

数据读写：

  • Redis集群有16384个哈希槽，每个key通过哈希运算后决定放到哪个槽中。
  • 每个节点负责一部分hash槽

Redis的多线程

对于Redis来说，CPU 通常不会是瓶颈，因为大多数请求不会是 CPU 密集型的，而是 I/O 密集型；

Redis 真正的性能瓶颈在于网络 I/O和内存

在以下场景里Reids会使用到多线程来异步操作：

  1. 删除超大的键值对：删除超大的对象耗时长，为了不阻塞主线程，Redis v4.0 之后增加了一些的非阻塞命令如 UNLINK、FLUSHALL ASYNC、FLUSHDB ASYNC。会先将key从keyspace删除，value由后台线程删除

  2. 读取客户端请求命令和回写响应数据：Redis 从 6.0 开始支持多线程处理客户端网络 I/O。I/O 线程读取和解析客户端命令而不会真正去执行命令，客户端命令的执行最终还是要在主线程上完成

Redis的 I/O多路复用

使用 I/O 多路复用机制并发处理来自客户端的多个连接

1. 客户端连接

Redis 服务端监听一个 TCP 端口。

客户端建立连接后，Redis 会：

  1. 接收客户端连接；
  2. 将客户端 Socket 设置为非阻塞模式；
  3. 将 Socket 注册到事件监听器中；
  4. 监听连接上的可读、可写等事件。

当某个 Socket 就绪时，Redis 才会处理对应事件。

2. 用户空间与内核空间

操作系统将内存和执行权限划分为：

  • 用户空间：应用程序运行的区域，不能直接访问硬件和关键系统资源。
  • 内核空间：操作系统内核运行的区域，可以管理 CPU、内存、网络和文件等资源。

Redis 接收网络数据时，数据通常经历：

3. 阻塞 I/O

线程调用读取操作后，如果数据尚未到达，线程会一直等待，直到：

  1. 内核准备好数据；
  2. 数据从内核空间复制到用户空间；
  3. 读取操作返回。

如果 Redis 主线程使用阻塞 I/O 处理某个客户端，就可能无法及时处理其他客户端。

4. 非阻塞 I/O

Socket 设置为非阻塞模式后，如果数据尚未准备好，读取操作会立即返回，不会一直等待。

应用程序需要不断轮询 Socket：

这种方式虽然不会长期阻塞线程，但频繁轮询会浪费大量 CPU。

数据准备完成后，从内核空间复制到用户空间的过程通常仍需要同步完成。

5. I/O 多路复用

I/O 多路复用允许一个线程同时监听多个 Socket。

线程通过 select、poll、epoll 或 kqueue 等系统调用，等待多个 Socket 的事件。当某个 Socket 可读或可写时，系统通知 Redis，Redis 再处理该 Socket。

它的核心特点是：

  • 一个线程可以管理大量客户端连接；
  • 不会阻塞在某一个客户端上；
  • 不需要不断轮询每一个 Socket；
  • 只有 Socket 就绪时才进行处理。
