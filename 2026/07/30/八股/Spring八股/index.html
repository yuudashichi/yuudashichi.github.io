Spring八股

Spring

IoC

Inversion of Control，控制反转。描述Java开发领域对象的创建以及管理的问题；

从自己控制依赖对象的创建，反转给容器控制对象的创建和依赖关系

IoC的好处：

  • 降低了类之间的耦合度：不是依赖具体的类，而是依赖接口，由容器来DI
  • 统一管理对象：方便替换实现、测试和扩展

DI

DI，Dependency Injection，依赖注入。DI 是实现 IoC 的主要方式

依赖注入的方式：

注入方式 示例 推荐程度
构造器注入 public UserService(UserDao userDao) 推荐，所有必需依赖在对象创建时就被注入；有助于创建不可变对象，提高了线程安全性；在单元测试中，可以直接通过构造函数传入模拟的依赖项，而不必依赖 Spring 容器进行注入
Setter 注入 setUserDao(UserDao userDao) 比较适合可选依赖或者确实需要后续修改依赖的情况
字段注入 @Autowired private UserDao userDao 不推荐。Spring创建对象后，通过反射给字段赋值。依赖关系隐藏在字段中，不够明确

注入Bean的注解：

  • @Autowired：Spring 内置的注解。先按类型匹配，若存在多个同类型 Bean，则再尝试按名称筛选，都不匹配则抛出异常
  • @Resource：源自 JSR-250 规范。默认取字段名去容器中查找，如果没有找到同名的 Bean，尝试根据字段的类型去查找，没找到或找到多个则抛出异常

Bean的作用域

  • singleton：默认，在IoC容器中只有一个实例
  • prototype：每次获取都会创建一个新的实例
  • request： 每一次 HTTP 请求都会产生一个新的 Bean，该 Bean 仅在当前 HTTP request 内有效
  • session： 每一次来自新 Session 的 HTTP 请求都会产生一个新的 Bean，该 Bean 仅在当前 HTTP session 内有效
  • global-session：每个 Web 应用在启动时创建一个 Bean，该 Bean 仅在当前应用启动时间内有效
  • websocket ：每一次 WebSocket 会话产生一个新的 Bean

Bean是否线程安全

有状态（有可变的成员变量）的Bean会出现共享状态竞争问题；

解决方式：

  • 避免可变成员变量
  • 使用ThreadLocal：将可变成员变量保存在 ThreadLocal 中，确保线程独立
  • 使用同步机制：使用锁来进行同步控制

Bean的生命周期

以下步骤按顺序执行：

  1. 读取并注册 BeanDefinition：对要放入容器的类，Spring会先生成对应的BeanDefinition，类似Bean的创建说明书

  2. BeanFactoryPostProcessor 处理 BeanDefinition：对BeanDefinition进行修改

  3. 实例化Bean：Spring会通过反射、构造器、工厂方法等方式创建对象

  4. 属性/依赖注入：对@Autowired、@Value等成员变量注入对应的值

  5. Aware接口回调：让 Bean 感知 Spring 容器自身的信息，将容器的信息通过回调函数的方式传入Bean中

  6. 执行BeanPostProcessor初始化前置处理：调用后处理器的postProcessBeforeInitialization()函数

  7. 初始化：

    1. 执行@PostConstruct：调用用此注解指定的初始化函数
    2. InitializingBean：实现这个接口的afterPropertiesSet()方法会在依赖注入后被调用
    3. 自定义初始化方法：通过@Bean(initMethod = "init")来指定自定义的初始化方法

  8. 执行BeanPostProcessor初始化后置处理 ：调用后处理器的postProcessAfterInitialization()函数，AOP代理通常在这产生

  9. 保存Bean、使用Bean

  10. 销毁Bean：Spring应用停止时开始销毁，使用@PreDestroy或实现DisposableBean接口或@Bean(destroyMethod = "close")来释放资源

Spring AOP

Aspect-Oriented Programming，面向切面编程。能够将那些与业务无关，却为业务模块所共同调用的逻辑或责任（例如事务处理、日志管理、权限控制等）封装起来，便于减少系统的重复代码

动态代理：

Spring不会直接修改源代码，而是通过创建代理对象来实现AOP。是否创建代理对象在BeanPostProcessor的初始化后置处理方法中判断

  • JDK动态代理：基于接口进行代理，代理类会实现相同的接口
  • CGLIB代理：基于继承进行代理，生成被代理类的子类

AOP常用通知：

多个切面可用Order()定义执行顺序

  • Before（前置通知）：目标对象的方法调用之前触发
  • After （后置通知）：目标对象的方法调用之后触发
  • AfterReturning（返回通知）：目标对象的方法调用完成，在返回结果值之后触发
  • AfterThrowing（异常通知）：目标对象的方法运行中抛出 / 触发异常后触发。AfterReturning 和 AfterThrowing 两者互斥。如果方法调用成功无异常，则会有返回值；如果方法抛出了异常，则不会有返回值。
  • Around （环绕通知）：编程式控制目标对象的方法调用。环绕通知是所有通知类型中可操作范围最大的一种，因为它可以直接拿到目标对象，以及要执行的方法，所以环绕通知可以任意的在目标对象的方法调用前后搞事，甚至不调用目标对象的方法

循环依赖

多个Bean对象之间循环引用，或者单个Bean自我依赖

三级缓存

解决字段 / Setter循环依赖；

通过构造函数来依赖注入，需要依赖的Bean存在才能实例化当前类，因此无法暴露前期对象，三级缓存解决不了这类循环依赖

  • 一级缓存：存放最终形态的Bean

  • 二级缓存：存放实例化、但尚未属性填充的Bean

  • 三级缓存：存放**ObjectFactory**，ObjectFactory的getObject()方法可以生成原始 Bean 对象或者代理对象

    三级缓存的作用是，在需要时能够 提前生成 AOP 代理对象，避免其他 Bean 拿到错误的原始对象

创建循环依赖Bean的流程：

  1. 如果允许循环依赖，在创建Bean的时候会向三级缓存中添加一个ObjectFactory对象
  2. 依赖注入时，依次检查三个缓存，如果前两层没有，会调用三级缓存的ObjectFactory.getObject()方法获取前期暴露对象，将对象放入二级缓存并移除ObjectFactory。
  3. 将这个前期暴露对象注入到依赖，来支持循环依赖。

@Lazy

@Lazy 用来标识类是否需要懒加载/延迟加载，可以作用在类上、方法上、构造器上、方法参数上、成员变量中；

@Lazy可以解决构造器循环依赖（不要在构造器、@PostConstruct 等 Bean 创建阶段过早调用这个懒加载依赖，否则可能让循环依赖重新出现）

给要注入的Bean加上@Lazy注解后，被标记的类会延迟加载，会先注入一个懒加载代理对象，第一次实际调用代理时再创建目标 Bean

启动流程

初始化容器

通过**this()**调用无参构造，主要做了：

  • 实例化**BeanFactory**，用于Bean的创建、存储和管理
  • 实例化**BeanDefinitionReader，用于读取有特定注解的类并转化成BeanDefinition**
  • 实例化**ClassPathBeanDefinitionScanner**，用于扫描指定包路径下的类，帅选出带有注解的类，交给BeanDefinitionReader解析为BeanDefinition
  • 注册内置Bean后置处理器：
    1. ConfigurationClassPostProcessor：BeanFactory后置处理器，核心职责是扫描配置类
    2. AutowiredAnnotationBeanPostProcessor：Bean后置处理器，核心职责是处理@Autowired、@Value注解的自动注入
    3. CommonAnnotationBeanPostProcessor：Bean后置处理器，处理@Resource、@PostConstruct、@PreDestroy等注解

将配置类注册到容器

调用**BeanDefinitionReader**将用户传入的配置类，转化为BeanDefinition

配置类作为入口，后续通过解析配置类的@ComponentScan、@Import、@Bean等，批量注册其他Bean

调用refresh()刷新容器

12个主要步骤

  1. prepareRefresh：初始化容器环境、校验属性合法性、保存早期事件，为后续刷新操作做准备
  2. obtainFreshBeanFactory：获取BeanFactory，确保BeanFactory是最新状态，避免因容器重复刷新导致的BeanFactory不一致问题
  3. prepareBeanFactory：BeanFactory预处理。向BeanFactory添加核心组件、设置基础配置，确保BeanFactory具备Bean创建和管理的基础能力
  4. postProcessBeanFactory：子类扩展预处理。在BeanFactory预处理完成后做进一步定制化配置
  5. invokeBeanFactoryPostProcessors：执行BeanDefinition的后置处理器，注册、处理和修改 BeanDefinition
  6. registerBeanPostProcessors：注册Bean后置处理器
  7. initMessageSource：初始化国际化组件
  8. initApplicationEventMulticaster：初始化事件派发器。负责事件的发布和监听器的管理，支撑Spring的事件驱动模型
  9. onRefresh：子类扩展刷新逻辑。在容器刷新过程中添加自定义组件
  10. registerListeners：注册监听器。将容器中的ApplicationListener注册到事件派发器中，并派发早期事件
  11. finishBeanFactoryInitialization：初始化容器中所有非懒加载的单例Bean，完成Bean的实例化、依赖注入、初始化方法执行等核心操作
  12. finishRefresh：完成容器刷新的收尾工作，发布容器刷新完成事件，初始化生命周期处理器

SpringMVC

MVC 是模型(Model)、视图(View)、控制器(Controller)的简写，其核心思想是通过将业务逻辑、数据、显示分离来组织代码

核心组件

  • DispatcherServlet：核心的中央调度器，负责接收请求、找Handler处理请求，并给予客户端响应
  • HandlerMapping：根据当前 HTTP 请求找到应该由哪个 Handler 处理，并会将请求涉及到的拦截器和 Handler 一起封装
  • **HandlerAdapter**：将不同类型的 Handler 适配成 DispatcherServlet 可以统一调用的方式
  • Handler：实际处理请求的业务入口，处理实际请求的处理器
  • **ModelAndView**：Handler的返回。包含 Model（数据）+ View（视图），不过现在一般都直接返回JSON数据
  • ViewResolver：视图解析器，根据 Handler 返回的逻辑视图 / 视图，解析并渲染真正的视图，并传递给 DispatcherServlet 响应客户端

工作流程

  1. 客户端发送请求，DispatcherServlet拦截请求
  2. DispatcherServlet根据请求信息调用HandlerMapping。HandlerMapping根据URL匹配能处理的Handler，并将涉及到的拦截器和Handler一起封装
  3. DispatcherServlet调用 HandlerAdapter适配器执行 Handler
  4. Handler处理请求并返回MoedlAndView / 字符串 / 对象等给DispatcherServlet
    • 如果是返回ModelAndView：
      1. ViewResolver 会根据逻辑 View 查找实际的View
      2. DispaterServlet把Model传给View进行视图渲染写入HttpServletResponse并返回
    • 如果是返回对象：
      1. 将对象序列化成JSON，写入HttpServletResponse并返回

统一异常处理

使用@ControllerAdvice + @ExceptionHandler统一处理请求

  1. Controller抛出异常，DispatcherServlet 找到匹配的 @ExceptionHandler
  2. 执行异常处理方法，返回ResponseEntity
  3. 序列化成JSON，写入HttpServletResponse并返回

事务

是否支持事务取决于数据库是否支持

事务相关接口：

  • PlatformTransactionManager：定义了获取事务getTransaction、提交事务commit、回滚事务rollback的函数
  • TransactionDefinition：定义了基本的事务属性，描述了事务策略如何应用到方法上。如隔离级别、传播行为、超时时间、是否只读
  • TransactionStatus：记录事务的状态

Spring事务管理方式：

  • 编程式事务：通过 TransactionTemplate或者TransactionManager手动管理事务
  • 声明式事务：使用@Transactional注解管理事务，基于AOP实现

事务的传播行为

解决业务层方法之间互相调用的事务问题

级别 描述
Required（默认） 当前存在事务则加入，否则新开启一个
Supports 加入当前事务，没有事务则以非事务的方式执行
Mandatory 加入当前事务，当前没事务则抛出异常
Requires_new 创建一个独立于当前的新事务
Not_supported 始终以非事务方式运行，不受外层事务影响
Never 仅支持非事务，当前有事务则抛出异常
Nested 在当前事务下创建子事务，跟随父事务提交/回滚，可以独立回滚

事务隔离级别

Spring 隔离级别 对应数据库隔离级别 脏读 不可重复读 幻读 说明
Isolation.DEFAULT 使用数据库默认级别 取决于数据库 取决于数据库 取决于数据库 Spring 默认值
Isolation.READ_UNCOMMITTED 读未提交 ✅ ✅ ✅ 隔离级别最低，可以读取未提交数据
Isolation.READ_COMMITTED 读已提交 ❌ ✅ ✅ 只能读取已经提交的数据

Isolation.SERIALIZABLE 串行化 ❌ ❌ ❌ 隔离级别最高，并发性能最低

事务失效场景

  • 场景1：检查异常

    需要 try..catch 或 throws 处理的异常通常属于检查异常
    RuntimeException 和 Error 属于非检查异常

    **原因**：Spring 默认只对 `RuntimeException` 和 `Error` 回滚，检查异常默认不回滚

**解决方式**：在注解上加 `@Transactional(rollbackFor = Exception.class)`

  • 场景2：错误 try catch

    原因：方法内部 catch 住异常且没有重新抛出，事务切面感知不到异常，会正常提交事务
  
**解决方式1**：把异常重新抛出去
  
**解决方式2**：手动设置事务回滚状态 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`

  • 场景3：AOP 切面顺序或异常处理不当

    **原因**：自定义切面 catch 住异常并吞掉，可能导致事务切面感知不到异常
  
**解决方式1**：自定义切面不要吞异常，继续向外抛出
  
**解决方式2**：根据实际需求使用 `@Order` 调整自定义切面和事务切面的执行顺序

  • 场景4：加在非公共方法上

    **原因**：Spring 基于代理实现事务，非 `public` 方法在不同代理方式和 Spring 版本下支持情况不同，容易导致事务无法按预期生效
  
**解决方式**：事务入口方法尽量使用 `public`

  • 场景5：父子容器导致事务失效

    **原因**：子容器扫描范围过大，把 Service 再次创建成一个没有事务增强的 Bean，Controller 可能注入了这个 Bean
  
**解决方式1**：父子容器分别扫描自己的包
  
**解决方式2**：避免不必要的父子容器结构

  • 场景6：调用本类方法导致传播行为失效

    **原因**：本类内部通过 `this.xxx()` 调用，没有经过 Spring 代理，因此被调用方法上的 `@Transactional` 不生效
  
**解决方式1**：将事务方法拆到另一个 Bean 中调用
  
**解决方式2**：注入自身代理对象，通过代理调用

  • 场景7：锁范围与事务范围不一致

    **原因**：`@Transactional` 的事务提交通常发生在目标方法返回之后，如果只在目标方法上加 `synchronized`，可能出现锁已经释放但事务还未提交的情况
  
**解决方式1**：将 `synchronized` 范围扩大到事务代理方法调用之外
  
**解决方式2**：使用数据库悲观锁，如 `select ... for update`

  • 场景8：对象没有交给 Spring 管理

    **原因**：自己通过 `new` 创建对象，不会经过 Spring 代理，因此 `@Transactional` 不生效
  
**解决方式**：让类成为 Spring Bean，并通过 Spring 容器获取对象

  • 场景9：事务类没有被 Spring 扫描

    **原因**：类所在包不在组件扫描范围内，Bean 没有被 Spring 管理，自然也不会创建事务代理
  
**解决方式**：调整 `@ComponentScan` 或 Spring Boot 启动类的包扫描范围

  • 场景10：数据库本身不支持事务

    **原因**：底层数据库或存储引擎不支持事务，即使 Spring 开启了事务也无法真正回滚
  
**解决方式**：使用支持事务的数据库和存储引擎，例如 MySQL InnoDB

  • 场景11：多数据源使用了错误的事务管理器

    **原因**：操作的是数据源 B，但 `@Transactional` 使用的是数据源 A 对应的 `TransactionManager`
  
**解决方式**：显式指定正确的事务管理器

  • 场景12：异步线程导致事务无法传播

    **原因**：Spring 事务通常通过 `ThreadLocal` 绑定到当前线程，`@Async` 开启新线程后不会自动继承原事务
  
**解决方式**：异步线程需要自己开启事务，不能依赖外层事务

  • 场景13：手动创建新线程

    **原因**：`new Thread()`、线程池等新线程不会自动继承当前线程的 Spring 事务
  
**解决方式**：新线程中的数据库操作需要独立事务控制

  • 场景14：传播行为因为自调用失效

    **原因**：例如同类中 `A()` 调用带 `REQUIRES_NEW` 的 `B()`，由于没有经过代理，`B()` 不会真正创建新事务

**解决方式**：将 `B()` 拆到其他 Bean 中，通过代理对象调用

    这个场景本质上属于场景6，但传播行为失效是非常常见的表现，建议单独记住。

常用注解

Spring Boot 基础注解

注解名 作用
@SpringBootApplication Spring Boot 应用的核心注解，通常标注在启动类上；组合了自动配置、组件扫描和配置类功能。
@EnableAutoConfiguration 启用 Spring Boot 自动配置，根据项目依赖和已有 Bean 自动配置应用。
@ComponentScan 扫描指定包下的 Spring 组件，如 @Component、@Service、@Repository 和 @Controller。

Spring Bean 注册与依赖注入

注解名 作用
@Component 将普通类注册为 Spring Bean，是通用的组件注解。
@Repository 标注持久层组件，并将其注册为 Spring Bean。
@Service 标注业务逻辑层组件，并将其注册为 Spring Bean。
@Controller 标注 Spring MVC 控制器，并将其注册为 Spring Bean。
@Bean 标注配置类中的方法，将方法返回的对象注册为 Spring Bean。
@Autowired 按类型自动注入 Spring Bean，可用于构造器、字段、Setter 方法或配置方法。
@Qualifier 当同一类型存在多个 Bean 时，通过名称指定需要注入的 Bean。
@Primary 将某个 Bean 标记为同类型 Bean 中的首选注入对象。
@Resource JSR-250/Jakarta 注入注解，默认优先按名称注入，也可通过 name 指定 Bean；不支持构造器注入。
@Scope 指定 Bean 的作用域，如 singleton、prototype、request、session、application 或 websocket。

Spring 配置相关注解

注解名 作用
@Configuration 声明一个类为 Spring 配置类，通常在类中通过 @Bean 定义 Bean。
@Value 注入配置文件中的单个属性，也支持 Spring 表达式语言 SpEL。
@ConfigurationProperties 将一组具有相同前缀的配置批量绑定到 Java 对象，适合结构化配置。
@PropertySource 加载指定的自定义配置文件，如 classpath 下的 .properties 文件。

Spring MVC 控制器与请求映射

注解名 作用
@Controller 声明传统 MVC 控制器，方法返回值通常作为逻辑视图名称。
@RestController 等价于 @Controller + @ResponseBody，方法返回值默认写入响应体，常用于 RESTful API。
@RequestMapping 将请求路径、HTTP 方法、请求参数或请求头等映射到控制器类或方法。
@GetMapping 映射 HTTP GET 请求。
@PostMapping 映射 HTTP POST 请求，通常用于创建资源。
@PutMapping 映射 HTTP PUT 请求，通常用于完整更新资源。
@DeleteMapping 映射 HTTP DELETE 请求。
@PatchMapping 映射 HTTP PATCH 请求，通常用于局部更新资源。
@ResponseBody 将方法返回值写入 HTTP 响应体，通常转换为 JSON 或 XML，而不是解析为视图名称。

Spring MVC 参数绑定

注解名 作用
@PathVariable 获取 URL 路径中的占位符参数，如 /users/{id} 中的 id。
@RequestParam 获取查询参数或表单参数，如 /users?name=Tom 中的 name。
@RequestBody 读取 HTTP 请求体，并通过 HttpMessageConverter 将 JSON 等数据转换为 Java 对象。

Bean Validation 数据校验

Spring Boot 2.x 通常使用 javax.validation.constraints，Spring Boot 3.x 及以上通常使用 jakarta.validation.constraints。

注解名 作用

@Validated Spring 提供的校验注解，支持分组校验和方法级校验。
@NotNull 被校验值不能为 null，但可以是空字符串或空集合。
@NotEmpty 值不能为 null，且字符串、集合、Map 或数组的长度不能为 0。
@NotBlank 字符串不能为 null，且去除首尾空白后长度必须大于 0。
@Null 被校验值必须为 null。
@AssertTrue / @AssertFalse 布尔值必须为 true / false。
@Min / @Max 数值必须大于等于指定最小值／小于等于指定最大值，主要用于整数类型。
@DecimalMin / @DecimalMax 校验数值的最小值／最大值，支持小数。
@Size 字符串、集合、Map 或数组的长度必须处于指定范围。
@Digits 限制数字整数部分和小数部分的最大位数。
@Pattern 字符串必须匹配指定的正则表达式。
@Email 字符串必须符合电子邮箱格式。
@Past / @Future 日期或时间必须位于当前时间之前／之后。
@PastOrPresent / @FutureOrPresent 日期或时间必须位于当前时间之前或等于当前时间／之后或等于当前时间。

SpringBoot

简化 Spring 开发减少配置文件，开箱即用

Starter作用

Spring Boot Starter本质是一个依赖集合，解决该引用哪些依赖的问题

主要做了：

  • 集合依赖：把某一类开发需要的依赖统一引入
  • 版本协调：配合 Spring Boot 的依赖管理，避免版本冲突
  • 降低配置成本

自动配置

**@SpringBootApplication**注解组成构成：

  • **@SpringBootConfiguration**：表示当前类是 Spring Boot 的配置类，本质上包含 @Configuration
  • **@EnableAutoConfiguration**：开启 Spring Boot 自动配置
  • **@ComponentScan**：自动扫描当前包及其子包中的 Spring Bean

自动装配：

  1. @EnableAutoConfiguration通过@import导入了**AutoConfigurationImportSelector** 类
  2. AutoConfigurationImportSelector会将所有自动配置类的全限定类名以 List 返回
  3. @Conditional 注解再按条件来选择要创建的Bean

读取配置文件

  • **@Value("${property}")**：加在变量上，用于读取比较简单的配置

  • **@PropertySource("classpath:配置文件名")**：指定读取的配置文件

  • **@ConfigurationProperties(prefix = "配置key名")**：加在类上，读取配置信息并与Bean绑定。

    需要使用@Component或@EnableConfigurationProperties(XXX.class)等方式将配置类注册成Bean

宽松绑定：

配置项名称不必和 Java 字段名完全一致，Spring Boot 会按配置来源进行规范化后再匹配；

推荐配置里用小写 + - 写法，Java字段使用驼峰命名

配置来源 支持的写法
.properties first-name、firstName、first_name
YAML first-name、firstName、first_name
JVM 系统属性 -D first-name、firstName、first_name
操作系统环境变量 大写字母和下划线，例如 FIRST_NAME

工具 默认映射规则 实现原理 适用场景
